# 9. Роли и админка

[← к плану](README.md) · продолжает S21, S19, Q7, F3, K10 из
`docs/public-launch-plan.md`.

## Что сейчас

- Админ — аккаунт, чьё **имя** есть в переменной `HANZI_ADMIN_USERS`
  (`server/src/http/routes/admin.ts:24`, сравнение по `usernameKey`).
  Проверка на сервере есть на каждом маршруте `/api/admin/*`; клиент
  спрашивает `GET /api/admin` только чтобы показать ссылку (`useIsAdmin`,
  `src/api/admin.ts`).
- `/admin` (`src/features/admin/AdminPage.tsx`, 215 строк): сделать
  приглашение; список аккаунтов (последний визит, устройства, место, с
  какого дня); журнал последних 60 событий; список приглашений.
- Нельзя: заблокировать, сбросить пароль, выдать права, отозвать
  приглашение, посмотреть расход по дням, увидеть активность, управлять
  контентом и настройками сайта. Часть — только командой
  `npm run admin` (`server/src/cli.ts`) с доступом к базе.

**Чем плох админ «по имени».** Имя — не личность: до исправления SEC6 его
можно было занять регистрацией; права нельзя выдать или снять без
перевыкладки; нет второго уровня («модератор контента» без доступа к
людям); нет записи, кто и когда стал админом.

## Принципы

1. **Роль — в базе, по id аккаунта.** Проверяет сервер, на каждом
   запросе, из свежей записи пользователя (не из cookie и не из клиента).
2. **Права не могут появиться у ученика через интерфейс.** Выдать роль
   может только существующий админ (с повторным вводом пароля) или команда
   на сервере. Нет маршрута, где клиент присылает свою роль.
3. **Админ не читает чужую работу.** Имена, даты, размеры, счётчики — да;
   тексты, записи голоса, разговоры — нет. Исключение — то, что ученик сам
   отправил (отзыв, жалоба, заявка на публикацию).
4. **Каждое действие админа — в журнал**, без возможности стереть.
5. **Опасное — с повторным вводом пароля** (SEC7) и подтверждением словом.

## Задачи

<a id="a1"></a>
### A1 (К) ✔ Роль и состояние аккаунта в базе

**Сделано (2026-11-11).** Колонки `role`, `status`, `flags` (JSON-текст в
обеих базах, читаются только известные ключи). Роль даётся из
`HANZI_ADMIN_USERS` один раз, пока в базе нет ни одного админа (посев
повторяется на каждом запросе, пока аккаунт с таким именем не появится);
дальше переменная нужна только для запрета регистрации этих имён (SEC6).
`requireRole('admin')` на всех `/api/admin/*`; роль читается из базы на
каждом запросе. Заблокированный: cookie и токены → 401, верный пароль →
403 `account_blocked`, неверный — как раньше; блокировка выходит везде и
отзывает токены. Последнего админа нельзя ни снять, ни заблокировать;
себя заблокировать нельзя. `npm run admin -- grant-admin | revoke-admin |
block | unblock`. Тесты: `server/test/roles.test.ts` (перебор всех
маршрутов `/api/admin/*` из `app.routes`), `postgres.test.ts`.

**Не сделано — вопрос владельцу.** Флаг `tutor` есть в базе, но
`HANZI_TUTOR_USERS` ещё решает сам. Сейчас «переменная не задана» значит
«Claude доступен всем» (домашний сервер). Если перенести её во флаг, после
удаления переменной нужно решить, что значит «ни у кого нет флага»:
(а) всем, как сейчас — просто, но флаг тогда ничего не ограничивает на
домашнем сервере; (б) никому, кроме админа — безопаснее для открытого
сайта, но владельцу на домашнем сервере придётся выдать флаг себе.
Рекомендация: (б), вместе с экраном флагов в A5. На Vercel Claude нет
вовсе, так что сегодня это касается только домашнего сервера.


- Колонки `users.role` (`learner` | `admin`; позже `editor`),
  `users.status` (`active` | `blocked`), `users.flags jsonb` (`tutor`,
  `unlimited`, `photoInbox`). Миграции в `postgres/migrations.ts` и
  `sqlite/`.
- Первичная выдача: при старте сервера имена из `HANZI_ADMIN_USERS`,
  **у которых уже есть аккаунт**, получают `role = admin`, если админов в
  базе нет вовсе (одноразовый посев), с записью в журнал. Дальше переменная
  не читается; `npm run admin -- grant-admin <name>` и `revoke-admin` — в
  `cli.ts`. `HANZI_TUTOR_USERS` так же переезжает во флаг `tutor`.
- `requireRole('admin')` в `server/src/http/guards.ts` рядом с
  `requireSession`: читает роль из пользователя сессии (`authenticate` уже
  загружает пользователя на каждый запрос — добавить поля в `UserDto` для
  сервера, **не** доверяя ничему из запроса).
- `status = blocked`: `authenticate` возвращает `null`, вход отвечает как
  на неверный пароль плюс отдельное сообщение только после верного пароля.
- `GET /api/auth/session` отдаёт `role` — клиенту для отрисовки; все
  решения — на сервере.
- Нельзя снять роль с последнего админа и заблокировать самого себя.

**Тесты (обязательны).** Ученик → 403 на каждый маршрут `/api/admin/*`
(перебором всех зарегистрированных маршрутов, чтобы новый маршрут без
проверки ронял тест); запрос с `role: "admin"` в теле или заголовке ничего
не даёт; заблокированный с живой cookie → 401; последний админ не
снимается.

**Готово, когда.** `HANZI_ADMIN_USERS` можно удалить из Vercel, и админ
остаётся админом.

<a id="a2"></a>
### A2 (В) Журнал действий админа

Расширить `audit_log` (или отдельная `admin_log`): `actor_id`, `action`,
`target_user_id`, `details jsonb`, `at`, `ip`. Пишется в той же транзакции,
что и действие. Действия: приглашение создано/отозвано, роль, блокировка,
сброс пароля, выход со всех устройств, кредиты, флаги, публикация и скрытие
книги, настройки сайта. Страница `/admin/log` с фильтром по действию и
человеку. Хранить год (сейчас 90 дней для входов — оставить для входов).

<a id="a3"></a>
### A3 (В) Блокировка и выход со всех устройств

В карточке пользователя: **Block** (причина обязательна; сессии
удаляются сразу; токены отзываются), **Unblock**, **Sign out everywhere**.
Заблокированный видит на входе: «This account is paused. Write to …».

<a id="a4"></a>
### A4 (В) Список пользователей, который выдержит 1000 человек

`GET /api/admin/users?q=&sort=&page=`: один запрос с агрегатами (последний
визит, место, расход за месяц, баланс кредитов, число текстов) вместо трёх
запросов на каждого (SEC14). Поиск по имени, сортировка (последний визит,
регистрация, расход, место), по 50 на страницу. Экран: строка на человека,
тап — карточка.

<a id="a5"></a>
### A5 (В) Карточка пользователя `/admin/users/:id`

- Кто: имя, с какого дня, последний визит, приглашение, по которому пришёл.
- Активность: дней с занятиями за 30 дней, минут, текстов прочитано,
  карточек отвечено, фраз сказано (счётчики — см. A7; не содержимое).
- Место: по видам (рабочее место, картинки, озвучки, попытки).
- Расход: по сервисам за месяц; кредиты — баланс и история (M8).
- Действия: выдать кредиты, флаги (`tutor`, `unlimited`, `photoInbox`),
  квота места, сброс пароля (A6), выход везде, блокировка, удаление
  (с вводом имени), роль.

<a id="a6"></a>
### A6 (В) Сброс пароля из админки

Админ не задаёт и не видит пароль. **Reset link**: одноразовый код (как
приглашение: случайный, в базе хэш, срок 24 часа), ссылка
`/recover?reset=…`, которую админ пересылает человеку сам; по ней человек
ставит новый пароль, все его сессии закрываются. Механизм — `recovery_codes`
и `RecoverPage` уже есть.

<a id="a7"></a>
### A7 (С) Дашборд: живёт ли сайт

`/admin` открывается сводкой:

- Сегодня / 7 дней / 30 дней: активных аккаунтов, новых, вернувшихся.
- Удержание: из зарегистрированных N недель назад — сколько занимались на
  1-й, 2-й, 4-й неделе (таблица когорт, без графиков).
- Воронка нового пользователя: зарегистрировался → прошёл первый запуск →
  открыл текст → добавил слово → ответил на карточку → вернулся на
  следующий день. Показывает, где теряются (проверка этапа 2).
- Что используют: чтение, карточки, речь, видео, игра — доля активных.
- Деньги: продано кредитов, потрачено, себестоимость, остаток пробных.

**Откуда данные.** Сейчас активность лежит внутри рабочего места
(`activity[day]` в JSON) — сервер её не видит. Сделать таблицу
`daily_activity(user_id, day, minutes, texts_read, answers, spoken)`:
клиент шлёт сводку дня отдельным маленьким запросом
(`POST /api/activity`, раз в несколько минут, со схемой и потолками
значений), сервер ничего из содержимого не получает. События воронки —
`POST /api/activity/event { kind }` из фиксированного списка. Без сторонней
аналитики (правило 7 старого плана). Сказать об этом в `/privacy`.

<a id="a10"></a>
### A10 (С) Расходы и выключатели (это Q7)

По сервисам за день и месяц: вызовы, единицы, оценка стоимости; кто

<a id="a11"></a>
### A11 (С) Настройки сайта

Таблица `site_settings(key, value jsonb, updated_at, updated_by)` с кэшем в
памяти на минуту. Ключи: режим регистрации, квота места по умолчанию,
размер пробного запаса, цены действий в кредитах, потолки, id готовых
голосов (K16), текст объявления (одна строка над Read, например о работах),
адрес формы отзывов. Каждое изменение — в журнал. Значения из переменных
окружения остаются значениями по умолчанию.

<a id="a12"></a>
### A12 (С) Отзывы (это F3)

`POST /api/feedback { kind, message, page }` (лимит 10 в день, 2000
знаков) → таблица `feedback` → `/admin/feedback` со статусом
(новое / отвечено / закрыто). Кнопка «Send feedback» в Me и на экране
ошибки тогда работает без внешней формы. Текст отзыва — пользовательский
ввод: показывать как текст, без разметки.

## Экран

`/admin` — тот же каркас «список разделов + раздел», что у настроек (P11):
Overview · Users · Invitations · Content · Costs · Feedback · Log ·
Settings. Адрес у каждого раздела и у каждой карточки. На телефоне всё
должно работать: владелец управляет сайтом с телефона (так записано в
README про приглашения).

Код: `src/features/admin/` по файлу на раздел; данные — через
`src/api/admin.ts`; типы — `shared/admin.ts`. Админский код грузить
отдельным куском (`lazy`), чтобы ученикам он не приходил (R10).
