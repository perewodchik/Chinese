# 6. Безопасность

[← к плану](README.md) · продолжает фазы 0–1 из `docs/public-launch-plan.md`
(S1–S23). Номера здесь — SEC1 и далее.

## Итог

Серверный код сделан аккуратнее, чем можно было ожидать: сессия — случайный
токен в HttpOnly cookie, в базе только его хэш; пароли — scrypt; запросы к
данным везде фильтруются по `userId` из сессии; SQL только с параметрами;
в клиенте нет `innerHTML`; CSP без внешних скриптов; админские маршруты
проверяют права на сервере. Проверено руками на локальном сервере: чужой
аккаунт получает 403 на `/api/admin/*`, запрос с чужого сайта — 403, не-JSON
— 400.

Слабые места — не в коде запросов, а **вокруг**: пароль админа в
репозитории, админ «по имени», dev-сервер на боевой базе, отсутствие ролей,
второго фактора и журнала действий админа.

<a id="sec1"></a>
## SEC1 (К) (владелец) Пароль админа боевого сайта в репозитории

**Состояние на 2026-11-11.** Пароль сменён владельцем; из
`.claude/skills/add-text/SKILL.md`, `.claude/skills/story/SKILL.md` и
`docs/photo-to-text.md` он убран, скиллы читают `HANZI_PASSWORD` из
окружения. Сделаны шаги 1 и 6; остальные — за владельцем.

**Где было.** В скилле `add-text` стояли имя, пароль и адрес сайта, с
пометкой, что это сделано сознательно. Для сайта одного человека это
был приемлемый риск; для сайта с другими учениками, админкой и деньгами —
нет: `admin`, скорее всего, и есть имя из `HANZI_ADMIN_USERS`.

**Что сделать, по порядку (сегодня).**
1. Войти на сайт, **Account › Password** — новый пароль: длинный,
   случайный, из менеджера паролей. Смена пароля выводит остальные
   устройства сама.
2. **Account › Recovery codes** — сделать заново (старые могли быть
   сделаны кем-то ещё).
3. **/admin › Lately** и **Invitations** — нет ли чужих входов и
   приглашений; **Accounts** — нет ли незнакомых.
4. Проверить ключи: если у аккаунта сохранены ключи SpeechSuper/MiniMax —
   посмотреть расход у поставщика; при сомнении перевыпустить.
5. В Vercel — убедиться, что заданы `HANZI_SECRETS_KEY` (иначе ключи
   учеников лежат в базе открытым текстом — S6) и `HANZI_ADMIN_USERS`.
6. Убрать пароль из `SKILL.md` (оба скилла) и из `docs/photo-to-text.md`:
   скилл читает `HANZI_PASSWORD` — а после SEC2 `HANZI_TOKEN` — из
   переменных окружения облачной среды (Environment variables в настройках
   среды) или из `.env` на Mac. История git пароль помнит — поэтому шаг 1
   обязателен и первый; чистить историю не нужно.
7. Включить secret scanning и push protection в настройках репозитория
   (S15: «включает владелец»).

**Готово, когда.** В файлах репозитория пароля нет; старый пароль не
подходит; скилл `/add-text` работает через переменную окружения.

<a id="sec2"></a>
## SEC2 (К) ✔ Токен для скриптов вместо пароля аккаунта

**Сделано (2026-11-11).** Таблица `api_tokens` в обеих базах (только
хэш), токен `hzw_` + 32 символа показывается один раз; `requireSession`
принимает `Authorization: Bearer` и не читает cookie, пускает токен только
на маршруты с его областью (`texts:write`: `/api/workspace`,
`/api/pictures`), остальным — 403, отозванный и истёкший — 401. Смена
пароля, восстановление и `admin reset-password` отзывают все токены.
`catalog:write` выдаётся только админу; маршрутов с ним пока нет (T1).
Экран — блок «Access tokens» на `/account` (подстраница Security появится
с P11). `book.ts`, скиллы и документы — на `HANZI_TOKEN`. Тесты:
`server/test/tokens.test.ts`, `postgres.test.ts`.

**Владельцу.** После выката: Account › Access tokens → Make a token →
`HANZI_TOKEN` в переменных облачной среды; `HANZI_PASSWORD` оттуда убрать.

**Что не так.** `scripts/texts/book.ts` (`siteAccount`, строка 604) входит
по имени и паролю и получает полную сессию: пароль аккаунта приходится
хранить там, где работает скилл. Украденный пароль = весь аккаунт.

**Что сделать.** Личные токены доступа:
- Таблица `api_tokens(id, user_id, name, digest, scopes, created_at,
  last_used_at, expires_at, revoked_at)`; в базе только хэш; токен
  показывается один раз, вид `hzw_<32 случайных символа>`.
- Области: `texts:write` (читать и сохранять рабочее место, класть
  картинки), `catalog:write` (публиковать в каталог, только у админа).
  Токен **не может**: менять пароль, удалять аккаунт, читать ключи,
  заходить в `/api/admin/*`, делать токены.
- Проверка — в `requireSession` (`server/src/http/guards.ts`): заголовок
  `Authorization: Bearer hzw_…` даёт «сессию» с `scopes`; маршруты, которым
  нужна полная сессия, отказывают токену. Запросам с токеном проверка
  `sameOriginOnly` не нужна (cookie нет), но и cookie при токене не
  читается.
- Экран: `Account › Security › Access tokens` — создать (имя, срок 90 дней
  по умолчанию), список с «последний раз использован», отозвать.
- `book.ts`: `HANZI_TOKEN` вместо `HANZI_USER`/`HANZI_PASSWORD`; старый
  способ убрать.

**С чего начать.** `server/src/application/ports.ts` (репозиторий),
миграции `postgres/migrations.ts` и `sqlite/`, `guards.ts`, тесты в
`server/test/http.test.ts` по образцу сессий.

**Готово, когда.** Скилл добавляет текст с токеном; с этим же токеном
`POST /api/auth/password` и `GET /api/admin/overview` дают 403; отозванный
токен — 401.

<a id="sec3"></a>
## SEC3 (В) (владелец) Dev-сервер на боевой базе пускает локальную сеть без пароля

**Что не так.** `server/src/dev.ts`: если в `.env` есть `POSTGRES_URL`, dev
работает на боевой базе (так задумано — `CLAUDE.md`), слушает `0.0.0.0`, а
`HANZI_DEV_USER=admin` входит без пароля с любого адреса локальной сети
(`isLocalNetwork`, `server/src/http/routes/auth.ts:44`). В домашнем Wi-Fi это
удобно; в кафе, коворкинге, на раздаче с телефона — любой сосед открывает
`http://<ip>:5173` и он админ боевого сайта.

**Что сделать.** Когда база — Postgres (`devUserCreate === false`):
- вход без пароля только с этой машины (127.0.0.1 / ::1);
- для планшета — явный флаг `HANZI_DEV_LAN=1` на один запуск, с
  предупреждением в баннере;
- либо (лучше) по умолчанию dev работает на локальной копии
  (`scripts/dev.sh --local`), а боевая база — по явному флагу.

Решение за владельцем: это меняет его привычный способ проверки на iPad.

<a id="sec4"></a>
## SEC4 (В) ✔ Лимит попыток входа на аккаунт

**Было.** `auth.perName` считался по паре «адрес + имя», `auth.perAddress` —
по адресу. Подбор одного аккаунта с тысячи адресов давал тысячу раз по 10
попыток за 15 минут.

**Сделано (2026-11-11).** `auth.perAccount`: 50 попыток в час на имя со
всех адресов вместе, сбрасывается при успешном входе; тот же счётчик
считает попытки восстановления по коду. Тест: `server/test/http.test.ts`,
«counts wrong passwords for one account from every address together».

**Осталось.** Обратная сторона — чужой может «занять» лимит и час не
пускать владельца. Смягчить: не считать против лимита вход из браузера, в
котором этот аккаунт уже успешно входил (отдельная долгоживущая cookie
`hanzi_known`, подписанная сервером). И строка в журнале (A2) при
срабатывании лимита — чтобы админ видел подбор.

<a id="sec5"></a>
## SEC5 (В) ✔ Потолок размера тела запроса

**Было.** Только `/api/workspace` и `/api/world` ограничивали тело. Вход,
регистрация, ключи, озвучка, картинки читали тело целиком и лишь потом
проверяли: 30 МБ в поле `password` сервер принимал, разбирал как JSON и
только затем отвечал 400 (проверено).

**Сделано (2026-11-11).** Общий потолок на `/api/*` — размер рабочего места
плюс запас (`tooLarge` в `server/src/http/app.ts`); `/api/auth/*` — 16 КБ;
`PUT /api/pictures/:key` — `PICTURE_MAX_BYTES` до чтения. Тест: «refuses a
body longer than a sign-in could be».

**Осталось.** Поставить свои потолки на `/api/eval` (аудио),
`/api/narration/texts/import` (MP3), `/api/talk/*` — сейчас их держит общий.

<a id="sec6"></a>
## SEC6 (В) ✔ Имена админов нельзя занять регистрацией

**Было.** Админ — тот, чьё имя есть в `HANZI_ADMIN_USERS`. Если имя
записано до создания аккаунта, или аккаунт админа удалён, первый, кто
зарегистрирует это имя, становится админом.

**Сделано (2026-11-11).** `AuthPolicy.reservedNames`: форма регистрации
отвечает «That name is taken» на имена из `HANZI_ADMIN_USERS`; такие
аккаунты создаёт только `npm run admin -- add-user`. Это заплатка до A1
(роль в базе по id).

<a id="sec7"></a>
## SEC7 (В) ✔ Повторный ввод пароля для опасных действий админа

**Сделано (2026-11-11).** `sessions.verified_at` (SQLite и Postgres;
у старых сессий — время создания) ставится при входе, регистрации и
восстановлении. `requireFresh` стоит на всех маршрутах админки, которые
что-то меняют (приглашения, пауза, открыть снова, выйти везде): если пароль
вводили больше 15 минут назад — 403 `reauth_required`; чтение не
спрашивает. `POST /api/auth/reauth { password }` — 10 попыток за 15 минут
на аккаунт, неверный пароль пишется в журнал входов (`reauth-refused`).
Клиент: `useFreshPassword` — лист «Your password, again», после пароля
действие повторяется само, «Not now» тихо отменяет. Срок: сессия админа
кончается через 7 дней после создания, как бы часто ею ни пользовались;
любая другая — через 180. Тесты: `server/test/fresh.test.ts`.

**Владельцу.** После выката сессии админа старше недели закончатся — войти
заново.


Сессия живёт 30 дней и продлевается при использовании
(`DEFAULT_AUTH_POLICY`). Украденная или забытая на чужом устройстве cookie
админа даёт всё. Сделать:
- «Свежая» сессия: поле `sessions.verified_at`; действия админа, которые
  что-то меняют (роли, блокировка, сброс пароля, кредиты, публикация,
  настройки сайта), требуют ввода пароля, если прошло больше 15 минут.
  Ответ сервера — `reauth_required`, клиент показывает лист с паролем и
  повторяет запрос.
- Для админа — срок сессии без продления 7 дней (у учеников — как сейчас).
- Абсолютный предел жизни сессии для всех — 180 дней от создания.

<a id="sec8"></a>
## SEC8 (С) Второй фактор для админа

TOTP (RFC 6238) — реализуется на `node:crypto` без зависимостей и без
платных сервисов: секрет хранится запечатанным (`SealedSecrets`), включение
— с подтверждением кодом, 8 запасных кодов (механизм уже есть —
`recovery_codes`). Для роли `admin` — обязателен; для учеников — по желанию.
Вход: пароль → код. Лимит попыток кода — как у пароля.

## Средняя важность

<a id="sec9"></a>
### SEC9 (С) Истёкшие сессии на Vercel не удаляются

`purgeExpiredSessions` вызывается только в `server/src/main.ts` (домашний
сервер, раз в час). На Vercel таблица `sessions` только растёт. Вызывать «с
вероятностью 1%» при входе, как `sweep` у лимитов, или из Vercel Cron
(входит в тариф) — тогда же чистить `rate_limits`, `lookup_cache`,
`audit_log`.

<a id="sec10"></a>
### SEC10 (С) Похожие имена

`usernameKey` — NFKC и нижний регистр; `NAME_SHAPE` разрешает любые буквы
Юникода. `bоss` (кириллическая «о») регистрируется рядом с `boss`
(проверено). Прав это не даёт, но в списках, отзывах и будущем общем
каталоге это чужое имя. Сделать: имя — буквы **одной** письменности
(латиница, или кириллица, или ханьцзы) плюс цифры и `._-`; список
запрещённых имён (`admin`, `administrator`, `root`, `support`, `moderator`,
`hanzi`, `system`, `staff`, `help`) в `shared/credentials.ts`.

<a id="sec11"></a>
### SEC11 (С) Приглашение сгорает при сбое

`AuthService.register`: приглашение помечается использованным **до** записи
аккаунта и возвращается только при `UsernameTakenError`. Любой другой сбой
вставки (база недоступна) — код потрачен, аккаунта нет. Обернуть в
транзакцию или возвращать при любой ошибке.

<a id="sec12"></a>
### SEC12 (С) Рабочее место не проверяется на сервере

`PUT /api/workspace` принимает любой JSON-объект с полем `version` до
16 МБ (`workspace-service.ts`, `isDocument`). Пока рабочее место видит
только владелец, это его дело. Как только появляются **общий каталог,
публикация и админский просмотр** (T1, A9), всё, что попадает из рабочего
места к другим людям, должно проходить схему (zod) на сервере: длины строк,
число строк, допустимые поля, никаких URL кроме своих `/api/pictures/…`.
Проверять на границе публикации, а не всё рабочее место.

<a id="sec13"></a>
### SEC13 (С) Картинки: один файл — один владелец

`PictureService.put`: одинаковая картинка у второго аккаунта отвергается
(«kept under another account») — это и утечка (S16), и поломка общего
каталога: ученик не сможет сохранить картинку, которая уже есть у админа.
Ключ хранения — `sha256(userId | bytes)` или составной первичный ключ
`(user_id, key)`; картинки каталога — отдельная таблица без владельца.

<a id="sec14"></a>
### SEC14 (С) Список пользователей в админке — по запросу на каждого

`GET /api/admin/overview` (`routes/admin.ts`) для каждого аккаунта делает
три запроса (сессии, место, расход). На 500 учениках это 1500 запросов и
таймаут функции. Один агрегирующий запрос, постраничная выдача, кэш на
минуту (A4).

<a id="sec15"></a>
### SEC15 (С) Журнал и оповещения

`audit_log` пишет входы, отказы, регистрации (S19). Добавить: срабатывание
лимитов, действия админа (A2), создание и отзыв токенов, смену ключей,
экспорт данных, удаление. В `/admin` — счётчик «неудачных входов за сутки»
и строка-предупреждение, если их больше N или если был вход админа с нового
устройства.

<a id="sec16"></a>
### SEC16 (С) Выход и localStorage

S5 сделан: данные в `localStorage` разделены по аккаунтам. Проверить после
SEC2/A1: при блокировке аккаунта и при «выйти везде» клиент на следующем
запросе получает 401 и очищает очередь отправки (не шлёт её следующему
вошедшему). Тест в `src/platform/accountStorage.test.ts`.

## Низкая важность и гигиена

<a id="sec17"></a>
- **SEC17 (Н)** `mayInspect` в `server/src/vercel.ts` сравнивает токен
  обычным `===`; заменить на `timingSafeEqual`.
- <a id="sec18"></a>**SEC18 (Н)** `recover()` отвечает быстрее для
  несуществующего имени (нет обращения к базе кодов). Регистрация и так
  сообщает, занято ли имя, поэтому это не новая утечка; выровнять заодно.
- <a id="sec19"></a>**SEC19 (Н)** `style-src 'unsafe-inline'` в CSP — из-за
  атрибутов `style={…}` (384 места). Убрать не срочно; не добавлять новых
  (R9).
- <a id="sec20"></a>**SEC20 (Н)** При подключении платежей и любых внешних
  виджетов CSP и `Permissions-Policy` (`payment=()`) правятся в двух местах
  — `shared/csp.ts` и `vercel.json` (тест сверяет). Платёжную страницу
  открывать переходом на сайт платёжного сервиса, без их скрипта на своих
  страницах — тогда CSP менять не надо.

## Правила на будущее (в `docs/development-standards.md`)

1. Права проверяет **сервер**, по роли из базы, на каждом маршруте.
   Клиентская проверка (`useIsAdmin`) — только чтобы не рисовать кнопку.
2. Каждый новый маршрут: сессия → роль → лимит → размер тела → схема тела →
   запрос с `user_id` из сессии. Тест «чужой аккаунт получает 404/403» —
   обязателен.
3. Секреты — только в переменных окружения сервиса. Ни в репозитории, ни в
   скиллах, ни в документации, ни «временно».
4. Ничего, что пришло от пользователя, не показывается другим пользователям
   без схемы на сервере.
5. Деньги и кредиты: только сервер, только добавляющая запись в книге,
   идемпотентность по id события (M2).
